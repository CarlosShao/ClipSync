# ClipSync 后台管理系统（Admin Console）落地方案

> 版本：v1.0（待人工审核）
> 定位：ClipSync 商用运营的统一管理面——用户、支付、审计、权限、系统配置
> 约束：仅管理员使用、并发极低 → **不引入**高并发/限流/微服务复杂度；最大化复用现有后端

---

## 1. 总体架构

```
┌─────────────────────────────┐     ┌──────────────────────────────┐
│  Admin Console SPA (静态)    │     │  现有 ClipSync Server (Node)  │
│  React + Vite + TS          │────▶│  + /api/admin/* 新路由组       │
│  组件库 + ECharts            │ JWT │  （复用 auth / RBAC / audit）  │
└─────────────────────────────┘     └──────────┬───────────────────┘
         nginx 托管静态资源                      │ 已有连接
                                    ┌───────────▼───────────┐
                                    │  PostgreSQL + Redis    │
                                    └───────────────────────┘
```

- **后端**：不新建服务。在 `src/server` 内新增 `src/routes/admin/` 路由组 + `src/middleware/adminAuth.js`（requireRole / requirePerm），挂载到 `/api/admin/*`。全部写操作自动经过现有 `superAdminAudit` 审计链。
- **前端**：全新独立 SPA（`src/admin-console/` 或独立目录），构建产物由 nginx 静态托管（建议子域 `admin.clipchain.top`，与 API 同域可省 CORS）。
- **鉴权**：复用现有 JWT + 会话体系；登录即走现有 `auth` 接口，前端按 `roleKey ∈ {super_admin, admin}` 决定能否进入；后端每个 admin 路由强制二次校验角色/权限（前端判断仅是 UX）。

## 2. 技术选型（两套候选，与 UI 草图一一对应）

| 维度 | 方案 A「Obsidian 暗色专业风」 | 方案 B「Daylight 亮色企业风」 |
|------|------------------------------|------------------------------|
| 框架 | React 18 + Vite + TypeScript | React 18 + Vite + TypeScript |
| 组件库 | **shadcn/ui**（Radix + Tailwind CSS） | **Ant Design 5** |
| 图表 | Recharts | ECharts 5 |
| 状态/请求 | Zustand + TanStack Query | Zustand + TanStack Query |
| 表格 | TanStack Table（shadcn 风格） | Ant Table（自带筛选/排序/分页） |
| 图标 | lucide-react | @ant-design/icons |
| 适配气质 | 深色、克制、工程感（Linear/Vercel 后台气质） | 亮色、高效、信息密度（阿里系运营后台气质） |

> 两版 UI 草图即按这两种气质手绘，**审核选定后即按对应组件库落地**，草图中的布局/信息结构直接映射组件。

## 4. Admin API 规划（`/api/admin/*`）

统一约定：全部挂 `authenticateToken` + `requireRole('admin')`（超管自动通过）；敏感操作另挂 `requirePerm('admin.xxx')`；写操作经 `superAdminAudit`；分页参数 `?page=&pageSize=&q=&sort=`；低并发场景不做缓存/限流。

```
GET    /api/admin/overview                 # 看板聚合指标（单接口返回全部 KPI + 时序）
GET    /api/admin/users                    # 列表（q= 手机哈希/昵称/ID，filters）
GET    /api/admin/users/:id                # 详情（含 devices/subscription/orders 摘要）
PATCH  /api/admin/users/:id/status         # { isActive: boolean, reason }
DELETE /api/admin/users/:id                # 软删/硬删（super_admin only）
PATCH  /api/admin/users/:id/role           # { roleId, reason }
POST   /api/admin/users/:id/force-logout   # 吊销全部会话
POST   /api/admin/users/:id/reset-2fa
GET    /api/admin/devices
DELETE /api/admin/devices/:id              # 远程下线
GET    /api/admin/subscriptions
POST   /api/admin/subscriptions/:id/grant  # 人工赠期/变更套餐 { planId, months, reason }
GET    /api/admin/orders                   # filters: status/channel/date
GET    /api/admin/orders/:orderNo
POST   /api/admin/orders/:orderNo/refund   # { amount, reason }（调用现有退款逻辑）
GET    /api/admin/reconciliation           # 对账汇总
GET    /api/admin/audit-logs               # filters: userId/action/date/ip/status
GET    /api/admin/roles                    # + permissions 目录
POST   /api/admin/roles                    # 自定义角色
PATCH  /api/admin/roles/:id/permissions
GET    /api/admin/plans  POST/PATCH /api/admin/plans/:id
GET    /api/admin/configs    PATCH /api/admin/configs/:key
GET    /api/admin/flags      PATCH /api/admin/flags/:key
POST   /api/admin/announcements           # 公告下发
GET    /api/admin/health                  # 聚合健康（含 slow-queries）
```

**权限目录扩展**（写入 `permissions` 表种子）：`admin.users / admin.devices / admin.subscriptions / admin.orders / admin.audit / admin.roles / admin.plans / admin.configs / admin.announce`，其中删除用户、退款执行、角色管理、系统配置默认**仅授予 super_admin**。

## 5. 交互与信息设计原则（去"AI 生成感"的具体做法）

1. **信息密度服务场景**：运营后台以表格为中心，行高紧凑、筛选常驻、列可排序；看板页才用卡片。
2. **数字用等宽数字（tabular-nums）**，金额右对齐、千分位、币种固定 ¥。
3. **状态一律用「色点+文字」胶囊**，不堆彩色大按钮；危险操作（停用/删除/退款）统一二次确认弹窗并要求填写原因。
4. **中性色为主，品牌紫 #5A4BD1 只做强调**（主按钮、选中态、链接、图表主色），杜绝大面积渐变。
5. 空态/加载态/错误态三态齐备；时间统一 `YYYY-MM-DD HH:mm` 相对时间辅助。
6. 手机号等敏感数据默认打码（138****1234），明文查看需点击并落审计。
