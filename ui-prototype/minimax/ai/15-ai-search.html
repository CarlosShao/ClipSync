What's the difference between WebSocket and Server-Sent Events, and when should I prefer one over the other in a real-time desktop sync app? ★ Pro
Streaming · 24 sources consulted · 3.2s
Sonar · Pro

WebSocket vs SSE: choose based on message direction, not speed

Both protocols push data over a single long-lived HTTP connection, but they differ in directionality. WebSocket is bidirectional — after the upgrade handshake either side can send messages at any time.1

1
MDN · WebSocket API
"WebSocket is a bidirectional communications protocol … makes it suitable for real-time apps."
Server-Sent Events is unidirectional — only the server can send data to the client.2
2
HTML Living Standard · Server-Sent Events
"An event stream is a unidirectional push from server to client over a single HTTP connection."

For a clipboard sync app the traffic is almost entirely server → device (the server tells clients "new item available"), with only rare client → server pings (ack, delete, mark-read). That asymmetry is exactly what SSE was designed for,3

3
Cloudflare Blog · Event-driven architectures
"For one-way fan-out from a single source to many subscribers, SSE is materially cheaper than WebSocket."
and you get auto-reconnect, ready-made `EventSource` browser API, and plain HTTP/2 multiplexing for free.

Reach for WebSocket only when you need true bidirectional traffic: collaborative cursors, in-app chat, gaming state, or interactive terminals.4

4
Ably Realtime · Protocol comparison
"WebSocket is the right choice when both peers need to publish messages with similar frequency."
For everything else, SSE is simpler, lighter on battery (no frame parsing, no ping/pong frames to keep alive),5
5
Mozilla Hacks · Battery-efficient real-time
"On mobile and laptops, SSE consumes measurably less power than a persistent WebSocket under low message rates."
 and works through more proxies without configuration.
