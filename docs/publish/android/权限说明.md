## 0. 一句话总述（可直接填到商店「权限说明」总述栏）

> ClipSync 是一款**跨设备剪贴板同步工具**。为在你的多台设备之间自动同步剪贴板内容，
> 应用需要在后台读取系统剪贴板、在你的手机与电脑之间传输数据、在你截屏时帮你把截图
> 同步到其他设备。因此申请了无障碍服务、通知使用权、前台服务、开机自启等权限。
> **应用不读取屏幕内容、不采集通讯录/短信/位置/相册原始照片，剪贴板内容仅在你本人
> 登录的账号与设备之间传输。**

## 2. 逐条权限说明

### 2.1 `INTERNET` —— 网络访问

- **权限名称**：网络访问 / INTERNET
- **为什么需要**：ClipSync 的全部价值建立在设备间传输上。应用需要把本机剪贴板内容
  上传到服务端、并接收其他设备推送的内容。原生侧上传实现在
  `src/mobile/android/app/src/main/kotlin/com/clipsync/clipsync_mobile/NativeClipboardUploader.kt`
  （`POST /api/clipboard`，见第 44 行），远程拉取实现在 `SyncForegroundService.kt`
  的 `pullRemoteImages()` / `httpGetString()`（第 800–950 行）。
- **不授予会怎样**：应用无法登录、无法同步，功能完全不可用。
- **不可替代性论证**：无网络能力的剪贴板同步应用没有存在意义，此为功能刚需。
  注意 Manifest 第 2 行注释明确说明：**release 包默认不含网络权限，必须显式声明**。

### 2.2 `USE_BIOMETRIC` —— 使用生物识别

- **权限名称**：使用生物识别 / USE_BIOMETRIC
- **为什么需要**：保护剪贴板历史不被他人翻看。用户可在设置页开启指纹/面容锁，
  打开应用时需生物识别验证。实现见
  `src/mobile/lib/services/biometric_service.dart`，配合 `local_auth` 依赖
  （`src/mobile/pubspec.yaml`，注释标注 "T4.6: 生物识别锁"）；
  承载 Activity 因此继承 `FlutterFragmentActivity`（`MainActivity.kt` 第 31 行，
  注释说明这是 local_auth 的硬性要求）。
- **不授予会怎样**：生物识别开关不可用，设置页显示"设备不支持生物识别"
  （`settings_screen.dart` 中 `l10n.biometricUnsupported` 分支）；应用其余功能正常。
- **不可替代性论证**：剪贴板历史属于高敏感个人数据（可能含密码、验证码、私密文本），
  生物识别是设备本地最强且**不采集任何生物特征原始数据**的保护手段。
  系统 API 只回传"验证成功/失败"布尔值，生物特征不出安全芯片。

### 2.3 `FOREGROUND_SERVICE` —— 前台服务

- **权限名称**：前台服务 / FOREGROUND_SERVICE
- **为什么需要**：剪贴板同步必须**持续常驻**——用户不会一直开着 App 界面，
  但复制行为随时发生。应用通过前台服务（常驻通知"ClipSync 同步运行中"）
  持有采集与同步能力。实现见 `SyncForegroundService.kt`（`startForegroundCompat()`，第 648 行）。
- **不授予会怎样**：应用启动服务时抛异常（`startForeground` 失败），后台同步能力全部失效。
- **不可替代性论证**：Android 8.0 起，任何需要"长时间后台运行"的应用**必须**使用前台服务，
  这是系统唯一合规的长驻后台机制（普通后台服务会被系统在数分钟内回收）。
  前台服务附带**用户可见的常驻通知**，本质是"对用户透明"的保活方式。

### 2.4 `FOREGROUND_SERVICE_DATA_SYNC` —— 前台服务（数据同步类型）

- **权限名称**：前台服务数据同步类型 / FOREGROUND_SERVICE_DATA_SYNC
- **为什么需要**：Android 10（API 29）起，前台服务必须声明**具体类型**；
  本应用在 API 29–33 上以 `dataSync` 类型启动（`SyncForegroundService.kt` 第 659–665 行）。
  数据同步正是剪贴板同步的准确语义归类。
- **不授予会怎样**：Android 10–13 设备上服务无法启动（`startForeground` 抛
  `MissingForegroundServiceTypeException`），后台同步完全失效。
- **不可替代性论证**：这是 Android 10+ 的**强制要求**，声明类型是启动前台服务的
  前提条件，非可选项。

### 2.5 `FOREGROUND_SERVICE_SPECIAL_USE` —— 前台服务（特殊用途类型）

- **权限名称**：前台服务特殊用途类型 / FOREGROUND_SERVICE_SPECIAL_USE
- **为什么需要**：Android 14（API 34）起，`dataSync` 类型的前台服务受
  **6 小时/24 小时运行上限**，且 Android 15 起**禁止从开机广播启动**。
  剪贴板同步需要全天候运行，因此 API 34+ 改用 `specialUse` 类型
  （Manifest 第 66–74 行，`SyncForegroundService.kt` 第 650–658 行），
  并在 Manifest 中通过 `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 声明子用途：
  > `Continuous clipboard and screenshot sync between the user's own devices`
  > （在用户自己的多台设备之间持续同步剪贴板与截图）
- **不授予会怎样**：Android 14+ 上服务启动失败；或被迫退回 `dataSync`，
  导致服务每 6 小时被系统强制停止，无法开机自启。
- **不可替代性论证**：`specialUse` 是 Google 为"无法归入既有类型、但对用户有明确
  且正当用途"的长驻服务设计的官方出口。本应用的子用途声明与该类型的设计意图完全吻合：
  **面向单个用户的私有设备间持续同步**，不涉及对外提供服务、不涉及商业内容分发。
  已按官方要求在 Manifest 声明用途字符串，可供审核直接核验。

### 2.6 `RECEIVE_BOOT_COMPLETED` —— 接收开机广播（开机自启）

- **权限名称**：接收开机完成广播 / RECEIVE_BOOT_COMPLETED
- **为什么需要**：用户重启手机后，希望同步**自动恢复**，而不是每次开机都手动打开
  App 一次。实现见 `BootCompletedReceiver.kt`：监听 `BOOT_COMPLETED` 与
  `QUICKBOOT_POWERON`（第 20 行），且**有严格的用户意愿门控**——
  仅当用户此前主动启动过同步（`serviceWanted == true`，第 21–30 行）才自启；
  用户主动停止同步或退出登录后，`stop()` 会清除该标记（`SyncForegroundService.kt` 第 208–213 行），
  开机不再拉起。
- **不授予会怎样**：重启手机后同步不会自动恢复，用户需手动打开 App；无其他影响。
- **不可替代性论证**：这是 Android 平台**唯一**能在开机阶段恢复应用状态的正规机制，
  不存在替代 API。且本应用的自启**尊重用户意愿**（不是无条件自启），
  符合工信部对"自启动"应可被用户控制的要求。

### 2.7 `POST_NOTIFICATIONS` —— 发送通知

- **权限名称**：发送通知 / POST_NOTIFICATIONS（Android 13+ 运行时权限）
- **为什么需要**：两个用途：(1) 前台服务的**常驻通知**（Android 系统强制要求前台服务
  必须显示通知，否则服务会被系统判定违规）；(2) 同步事件提醒（如"设备 B 已同步一条内容"）。
  运行时申请逻辑见 `MainActivity.kt` 的 `requestNotificationPermission()`
  （第 215–237 行），使用标准 `requestPermissions()` 弹窗。
- **不授予会怎样**：无常驻通知（部分 ROM 下前台服务会被系统降级/停止），
  无同步提醒；**剪贴板同步本身仍可工作**，属于体验降级而非功能失效。
- **不可替代性论证**：Android 13+ 强制的运行时权限，**由用户自主决定**，
  应用不申请也无法展示任何通知。本应用将其作为"可选增强"而非强制，
  拒绝后不影响核心同步，符合最小干扰原则。

### 2.8 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` —— 请求忽略电池优化

- **权限名称**：请求忽略电池优化 / REQUEST_IGNORE_BATTERY_OPTIMIZATIONS
- **为什么需要**：Android 6.0 起引入 Doze（低电耗）模式，息屏后系统会冻结后台网络
  与定时器，导致剪贴板同步在息屏时中断——而息屏恰恰是用户复制内容后最常放下手机的
  时刻。应用在引导页提示用户将 ClipSync 加入电池优化白名单，
  实现见 `SyncForegroundService.kt` 的 `isIgnoringBatteryOptimizations()`
  与 `requestIgnoreBatteryOptimizations()`（第 223–242 行）。
- **不授予会怎样**：息屏后同步可能延迟或中断，需用户亮屏后补同步；应用其余功能正常。
- **不可替代性论证**：**本权限只是"打开系统设置页"的入口，应用无法自行获得豁免**——
  `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 会跳转到系统原生弹窗
  （第 234–238 行），最终是否豁免**完全由用户在系统 UI 中点击决定**。
  这符合 Google 对"应用应引导用户手动加白名单"的合规建议，且不涉及静默提权。

### 2.9 `WAKE_LOCK` —— 保持唤醒

- **权限名称**：唤醒锁 / WAKE_LOCK
- **为什么需要**：截屏发生时，系统可能正处于休眠。为完成"读取截图文件 → 上传到服务端"
  这一段必须连续完成的操作，应用会短暂持有 `PARTIAL_WAKE_LOCK`（默认 15 秒，
  截图链路 20 秒）。实现见 `SyncForegroundService.kt` 的
  `acquireWakeLock()` / `releaseWakeLock()`（第 350–395 行）。
- **不授予会怎样**：息屏/锁屏状态下截图同步容易失败，需亮屏后重试。
- **不可替代性论证**：`PARTIAL_WAKE_LOCK` 只保持 CPU 运行、**不点亮屏幕**，
  对电量影响极小，且设有**明确超时**（`acquire(durationMs)`，非无限持有），
  用完立即释放。这是 Android 官方为"短时完成关键后台任务"设计的标准手段。

### 2.10 `ACCESS_WIFI_STATE` —— 读取 Wi-Fi 状态

- **权限名称**：访问 Wi-Fi 状态 / ACCESS_WIFI_STATE
- **为什么需要**：配合 Wi-Fi 高性能锁（`WifiLock`）使用，在传输截图等较大数据时
  避免 Wi-Fi 进入省电休眠导致传输中断。实现见 `SyncForegroundService.kt`
  第 361–376 行（`createWifiLock(WIFI_MODE_FULL_LOW_LATENCY)`）。
- **不授予会怎样**：传输大图时可能因 Wi-Fi 休眠而变慢或重试。
- **不可替代性论证**：创建 `WifiLock` 必须先持有本权限，这是 Android API 的硬性依赖。
  **本权限只能读取 Wi-Fi 连接状态，无法读取 Wi-Fi 密码、无法获取用户网络位置。**

### 2.11 `CHANGE_WIFI_MULTICAST_STATE` —— 更改 Wi-Fi 多播状态

- **权限名称**：更改 Wi-Fi 多播状态 / CHANGE_WIFI_MULTICAST_STATE
- **为什么需要**：用于局域网内设备发现/直连场景，提升同一 Wi-Fi 下多设备传输的稳定性。
- **不授予会怎样**：同 Wi-Fi 局域网直连的稳定性下降，回退走公网服务端中转。
- **不可替代性论证**：多播相关的系统 API 均受此权限保护，属技术依赖。
  本权限**不涉及任何用户隐私数据读取**，仅影响 Wi-Fi 芯片的多播过滤状态。

### 2.12 `READ_EXTERNAL_STORAGE` —— 读取外部存储（仅 Android 12 及以下）

- **权限名称**：读取外部存储 / READ_EXTERNAL_STORAGE
- **为什么需要**：截图同步功能需要读取系统相册中新生成的截图。
  在 Android 12（API 32）及以下，读相册需要此权限。Manifest 第 20 行已加
  `android:maxSdkVersion="32"` 限定，**Android 13+ 不会申请此权限**。
- **不授予会怎样**：Android 12 及以下无法自动同步截图，剪贴板文本同步不受影响。
- **不可替代性论证**：低版本 Android 的唯一可用 API。已通过 `maxSdkVersion`
  限制作用范围，在支持新 API 的系统上主动放弃申请，符合最小权限原则。
  **本应用只读取"截图"类图片（通过系统相册接口 + 截屏目录监听），
  不做全盘文件扫描。**

### 2.13 `WRITE_EXTERNAL_STORAGE` —— 写入外部存储（仅 Android 9 及以下）

- **权限名称**：写入外部存储 / WRITE_EXTERNAL_STORAGE
- **为什么需要**：把电脑端发来的图片保存到手机相册（`Pictures/Screenshots`）。
  Android 9（API 28）及以下需此权限；Android 10+ 改用 `MediaStore` 分区存储，
  无需该权限。Manifest 第 21 行已加 `android:maxSdkVersion="28"`。
- **不授予会怎样**：Android 9 及以下无法把图片存进相册，其余功能正常。
- **不可替代性论证**：同 2.12，为低版本系统的历史 API 依赖，已限定版本范围。
  写入位置固定为系统标准的 `Pictures/Screenshots` 目录（`SyncForegroundService.kt`
  第 282、319–322 行），不写入其他任何位置。

### 2.14 `READ_MEDIA_IMAGES` —— 读取图片（Android 13+）

- **权限名称**：读取图片媒体 / READ_MEDIA_IMAGES
- **为什么需要**：Android 13（API 33）起，`READ_EXTERNAL_STORAGE` 被细分为
  `READ_MEDIA_IMAGES` / `READ_MEDIA_VIDEO` / `READ_MEDIA_AUDIO`。本应用**只申请图片**
  一项（不需要视频、音频），用于截图同步。运行时申请见 `MainActivity.kt`
  `requestMediaReadPermission()`（第 277–292 行），按 SDK 版本自动选择
  `READ_MEDIA_IMAGES` 或 `READ_EXTERNAL_STORAGE`。
- **不授予会怎样**：Android 13+ 无法自动同步截图，剪贴板文本同步不受影响。
- **不可替代性论证**：已遵循 Android 13 的**权限细分**要求，只取图片一类，
  不申请视频/音频权限。这是"按需最小化"的直接体现。

### 2.15 `BIND_ACCESSIBILITY_SERVICE` —— 无障碍服务 ★重点

- **权限名称**：绑定无障碍服务 / BIND_ACCESSIBILITY_SERVICE
  （声明于 `ClipboardAccessibilityService`，Manifest 第 99–110 行）
- **为什么需要**：
  **这是本应用最关键、也最容易被审核质疑的权限，原因如下。**

  Android 10（API 29）起，系统为保护隐私**禁止无输入焦点的应用读取剪贴板**：
  只有"当前拥有输入焦点的应用"与"默认输入法"能拿到 `ClipboardManager.primaryClip`，
  其他应用一律返回 `null`。而前台服务**永远没有输入焦点**——
  这意味着仅靠前台服务的经典采集链路，**在后台/锁屏时读到的永远是空内容**，
  "手机复制 → 电脑粘贴"只在 App 前台打开时才生效，完全无法满足产品定位。

  **无障碍服务是系统信任组件（AccessibilityService），被明确豁免此剪贴板焦点限制**，
  在后台与锁屏状态下均可读取剪贴板。这是当前 Android 平台上，
  **第三方应用实现"后台剪贴板同步"的唯一合规技术路径**——与输入法读取剪贴板的
  系统授权层级同源。

  实现细节（`ClipboardAccessibilityService.kt`）：
  - 屏幕亮起时每 2 秒轮询一次系统剪贴板（`POLL_INTERVAL_MS = 2000`，第 46 行），
    `SCREEN_ON` / `USER_PRESENT` 时立即补扫（第 118–134 行）
  - 采集到的文本经 `NativeClipboardUploader` 上传（第 208 行）
  - 只在文本类型且非空白、长度 ≤ 100,000 字符时采集（第 178–188 行）
  - 回声抑制：Dart 侧回写的内容 60 秒内不再上传，避免回环（第 48–74 行）

- **🌟 重要：本服务不读取屏幕内容**
  无障碍服务配置见 `src/mobile/android/app/src/main/res/xml/accessibility_service_config.xml`，
  其中 **`android:canRetrieveWindowContent="false"`** ——
  这明确关闭了"读取窗口内容"能力，即**本服务在技术上无法读取你屏幕上的任何文字、
  控件或界面内容**。它声明的 `accessibilityEventTypes` 仅为 `typeWindowStateChanged`，
  且 `onAccessibilityEvent()` 实现为**空方法**（`ClipboardAccessibilityService.kt`
  第 160–162 行，源码注释："不消费无障碍事件：采集靠轮询，服务本身只为获取系统信任豁免"）。

  服务描述字符串（`res/values/strings.xml` 第 4 行）也向用户明示：
  > "让 ClipSync 在后台读取系统剪贴板并与你的其他设备同步（Android 10+ 限制下，
  > 后台读取剪贴板必须通过系统信任的无障碍服务）。ClipSync 不读取屏幕内容、
  > 不收集任何其他数据。"

- **不授予会怎样（功能降级说明）**：
  - 后台/锁屏状态下**无法自动采集剪贴板**，"手机复制 → 电脑粘贴"退化为
    **仅 App 前台时可用**
  - 保留可用路径：**通知栏「同步剪贴板」按钮**与**快捷设置磁贴**（下拉面板一键同步），
    这两条路径通过透明 `QuickSyncActivity` 借输入焦点读取剪贴板
    （`QuickSyncActivity.kt`），**不依赖无障碍服务**
  - **其他所有功能不受影响**：登录、剪贴板列表/搜索/过滤、电脑 → 手机的同步
    （前台服务原生轮询 `pullRemoteImages()` 负责写入手机剪贴板）、截图同步、
    收藏、模板、设置等
  - 应用**不会**因未授予无障碍权限而无法使用或反复骚扰用户

- **如被商店质疑，如何论证不可替代（答辩要点）**：

  | 审核可能的质疑 | 答辩要点 |
  |----------------|----------|
  | "为什么不用普通剪贴板 API？" | Android 10（API 29）起，`ClipboardManager.getPrimaryClip()` 对无输入焦点的应用**返回 null**（系统隐私限制，见 [Android 官方文档](https://developer.android.com/about/versions/10/privacy/changes#clipboard-data)）。前台服务没有输入焦点，普通 API 在后台/锁屏下**必然拿不到数据**。这不是实现选择问题，是平台硬限制。 |
  | "能否用前台服务 + 轮询替代？" | 不能。`SyncForegroundService` 中保留的经典采集链路（第 984–1035 行 `readClipboard()`）在有输入焦点时可用，但服务本身无焦点，源码注释已说明该路径"受 Android 10+ 焦点限制只能在 App 前台工作"。所以代码中第 987 行明确：`if (ClipboardAccessibilityService.isConnected) return`——无障碍已接管时让位，避免重复采集。 |
  | "为什么不用输入法？" | 输入法同样享有剪贴板豁免，但要求用户**替换系统默认输入法**——这是对用户更高的侵入性要求，且 ClipSync 并非输入法产品，做输入法属于功能与资质错配。无障碍服务是本场景下**侵入性最低**的合规路径。 |
  | "是否过度读取用户数据？" | 不。已通过 `canRetrieveWindowContent="false"` **从技术上关闭窗口内容读取能力**，`onAccessibilityEvent()` 为空实现，不消费任何无障碍事件。服务只做"轮询系统剪贴板 → 上传"一件小事。可在审核时提供该配置文件作为证据。 |
  | "用户是否知情并同意？" | 是。无障碍权限**无法静默获取**，必须在系统设置中由用户手动开启，且系统会展示应用提供的用途说明字符串（`accessibility_service_desc`，见 `strings.xml`）。应用内还有专门的权限引导页 `src/mobile/lib/screens/onboarding/permission_guide_screen.dart`，向用户解释用途。 |
  | "剪贴板内容是否回传服务器？" | 在用户**本人账号的设备之间**传输。内容经服务端加密存储（`src/server/src/utils/encryption.js`，AES-256-GCM；设备间密钥交换见 `src/server/src/utils/keyExchange.js`，ECDH + PBKDF2 派生）。**不做任何内容分析、不用于广告、不向第三方共享。** |

- **⚠️ 审核风险提示（诚实记录）**：无障碍权限是国内安卓商店**人工审核最严格**的一类，
  华为/小米均可能要求补充说明或要求提供"权限使用场景录屏"。
  建议提交时**主动**在权限说明栏粘贴本节要点，尤其是
  `canRetrieveWindowContent="false"` 这一条技术证据，可显著降低被打回概率。

### 2.16 `BIND_NOTIFICATION_LISTENER_SERVICE` —— 通知使用权

- **权限名称**：绑定通知监听服务 / BIND_NOTIFICATION_LISTENER_SERVICE
  （声明于 `KeepAliveNotificationListener`，Manifest 第 88–96 行）
- **为什么需要**：**两个用途，其中第二个是核心卖点功能。**

  1) **保活锚点**：通知监听服务由系统托管绑定，进程被杀后系统会自动重绑
     （`KeepAliveNotificationListener.kt` 第 45–48 行），与无障碍服务一同构成
     应用在厂商 ROM 强清理下的存活保障。
  2) **验证码自动接力（杀手场景）**：手机收到含验证码的短信/通知时，
     应用自动提取其中的验证码并推送到服务端，电脑剪贴板立即变为该验证码，
     用户直接在电脑上 Ctrl+V —— 覆盖"手机收验证码 → 电脑粘贴"这一高频场景，
     比手动"复制再同步"快一步。

  **隐私关键点**：应用**只上传提取出的验证码数字本身，不上传短信全文**
  （源码第 17 行注释明确说明，第 74 行 `uploadAsync(applicationContext, code)`
  上传的是 `code` 变量而非原文）。提取规则严格：通知文本须含验证码关键词
  （验证码/校验码/动态码/OTP/code 等，第 33–36 行）才触发，
  且只取关键词后最近的 4–8 位纯数字（`CODE_PATTERN = Regex("\\d{4,8}")`，第 37 行）。
  超过 600 字符的通知文本直接跳过（第 58 行），本应用自身通知与系统常驻通知跳过
  （第 55–56 行）。同一验证码有 120 秒去重窗口（第 28 行）。

- **不授予会怎样**：
  - 验证码自动接力不可用 → 用户需手动复制验证码（**主流剪贴板应用的标准流程**）
  - 失去一个保活锚点，厂商 ROM 下服务被杀后恢复速度略降
  - **剪贴板同步、截图同步等核心功能完全不受影响**
- **不可替代性论证**：
  - 读取通知内容在 Android 上**只有** `NotificationListenerService` 一条路径，
    无替代 API
  - "验证码自动填到电脑"是该能力的**唯一正当用途**，且已做**数据最小化**：
    只取 4–8 位数字，不落地、不存储、不上传短信全文
  - 该权限同样**必须用户在系统设置手动开启**，系统会展示用途说明
  - 应用内提供跳转入口 `openNotificationListenerSettings()`
    （`MainActivity.kt` 第 177–187 行），由用户主动决定

### 2.17 `BIND_QUICK_SETTINGS_TILE` —— 快捷设置磁贴

- **权限名称**：快捷设置磁贴 / BIND_QUICK_SETTINGS_TILE
  （声明于 `QuickSyncTile`，Manifest 第 119–128 行）
- **为什么需要**：在系统下拉快捷面板提供「同步剪贴板」按钮。
  用户在任何界面复制文字后，下拉面板点一下即完成手机 → 电脑同步，
  **无需切换应用**。实现见 `QuickSyncTile.kt`（`onClick()` 拉起透明
  `QuickSyncActivity` 借焦点读取并上传剪贴板）。
- **不授予会怎样**：失去下拉面板快捷入口；可通过通知栏按钮或直接打开 App 完成同样操作。
- **不可替代性论证**：磁贴是 Android 7.0+ 官方提供的应用快捷入口机制，
  由用户**在系统面板中手动添加**才出现，应用无法强制添加。
  本权限**不授予应用任何数据访问能力**，仅为 UI 入口声明。

1. **不申请**：定位、通讯录、短信读取（`READ_SMS`）、通话记录、相机（除用户主动

## 4. 专项分析：`android:usesCleartextTraffic="true"` 的安全风险与整改建议

> **本节仅为分析与建议。按任务要求，本次**未修改** `AndroidManifest.xml`——
> 该改动会影响真机调试链路，需由项目负责人决策后再实施。**
> 涉及文件：`src/mobile/android/app/src/main/AndroidManifest.xml` **第 28 行**。

### 4.1 现状

```xml
<application
    android:label="ClipSync"
    android:name="${applicationName}"
    android:icon="@mipmap/ic_launcher"
    android:requestLegacyExternalStorage="true"
    android:usesCleartextTraffic="true">     <!-- ← 第 28 行 -->
```

### 4.2 风险说明

`android:usesCleartextTraffic="true"` 表示**应用允许所有明文 HTTP（非 HTTPS）流量**。
即使目标 URL 写的是 `http://`，或某个中间环节发生了 HTTPS 降级，系统都不会拦截。

具体风险：

| 风险 | 说明 |
|------|------|
| **传输内容可被窃听** | 剪贴板内容可能包含密码、验证码、私密聊天文本、API Key 等高度敏感信息。明文 HTTP 下，同一 Wi-Fi 内的攻击者（或运营商中间节点）可**直接读取全部内容**。 |
| **可被中间人篡改** | 明文中转节点可篡改上传内容或响应，例如把验证码替换为攻击者指定的值。 |
| **应用全局放行** | 该属性是**应用级别**的——不只放行你的测试服务器，而是放行应用发起的**所有** HTTP 请求，包括第三方 SDK 的请求。攻击面被无谓放大。 |
| **商店审核风险** | 国内各商店的安全检测（如应用宝腾讯云测试、华为安全检测）**通常会把明文传输标为高危项**，可能导致审核不通过或被要求整改。 |
| **备案合规风险** | 与隐私政策中"传输加密"的表述冲突，存在合规陈述不一致的风险。 |

**根因推测**（需项目确认）：大概率是为了让**开发环境的 `http://` 测试服务器**
（如局域网 IP 的 dev 后端）能在真机上连通而临时开启的。

### 4.3 整改建议（推荐方案：`networkSecurityConfig` 白名单）

**目标**：只在开发阶段放行指定的明文地址，**生产环境默认全面禁止明文**。

**第 1 步**：新建 `src/mobile/android/app/src/main/res/xml/network_security_config.xml`

```xml
<?xml version="1.0" encoding="utf-8"?>
<network-security-config>
    <!-- 生产默认：禁止一切明文流量 -->
    <base-config cleartextTrafficPermitted="false">
        <trust-anchors>
            <certificates src="system" />
        </trust-anchors>
    </base-config>

    <!-- 仅在 debug 构建放行本地开发服务器（真机调试链路） -->
    <debug-overrides cleartextTrafficPermitted="true">
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
    </debug-overrides>
</network-security-config>
```

> `debug-overrides` 只在 `android:debuggable="true"` 的构建中生效，
> **release 包自动不受影响**——这正是"开发放行、生产禁止"的官方机制。

**第 2 步**：修改 Manifest 第 28 行

```xml
<application
    android:label="ClipSync"
    android:name="${applicationName}"
    android:icon="@mipmap/ic_launcher"
    android:requestLegacyExternalStorage="true"
    android:networkSecurityConfig="@xml/network_security_config">
    <!-- 移除 android:usesCleartextTraffic="true" -->
```

**第 3 步（如需按域名精确放行）**：若开发服务器不能用 `debug-overrides` 覆盖
（例如 release 测试包也要连内网），改为按域名白名单：

```xml
<domain-config cleartextTrafficPermitted="true">
    <domain includeSubdomains="false">192.168.1.100</domain>  <!-- 开发机 IP -->
    <domain includeSubdomains="false">10.0.2.2</domain>       <!-- Android 模拟器宿主 -->
</domain-config>
```

### 4.4 ⚠️ 为什么本次没有直接改（需项目负责人决策）

1. **会影响真机调试链路**：按 AGENTS.md，移动端调试走 **USB 真机 + dev 环境后端**。
   若 dev 后端或当前 `server_config` 使用的是 `http://` 地址，
   移除 `usesCleartextTraffic` 后**会立即导致真机连不上后端**，
   需同步确认 `src/mobile/lib/services/server_config.dart` 中的默认地址协议。
2. **需先确认生产环境已全量 HTTPS**：包括 API、媒体下载、WebSocket
   （当前原生侧 `httpGetString` / `NativeClipboardUploader` 使用 `HttpURLConnection`，
   URL 来自运行时配置的 `baseUrl`）。
3. **改动需重新构建 + 真机回归**：属于会改变 `AndroidManifest.xml` 的结构性修改，
   按项目约定不由本任务擅自实施。

### 4.5 建议的验证清单（实施整改后）

- [ ] 确认 `server_config.dart` 中**生产默认地址为 `https://`**
- [ ] 确认 dev 环境地址仍能在 debug 包下连通（`debug-overrides` 生效）
- [ ] release 包抓包验证：非白名单域名的 `http://` 请求被系统拒绝
      （预期抛 `CleartextNotPermittedException`）
- [ ] 各商店安全检测项复测，确认"明文传输"高危项消失
- [ ] 同步更新隐私政策中关于传输加密的表述（如已声称全链路加密）

## 5. 审核问询速查（常见问题标准答复）

**Q：为什么一个剪贴板工具要无障碍权限？是不是在偷看用户屏幕？**
A：不用无障碍就实现不了后台同步——Android 10 起禁止无焦点应用读剪贴板，
无障碍是系统唯一豁免的合规路径。而且我们**在配置里关闭了窗口内容读取**
（`canRetrieveWindowContent="false"`），服务代码里 `onAccessibilityEvent()` 是空的，
技术上就读不到屏幕内容。可以现场提供该配置文件核验。

**Q：为什么需要通知使用权？**
A：主要做验证码自动接力——手机收到验证码短信时，自动把验证码同步到用户电脑，
用户直接粘贴。**只取那 4–8 位数字，短信全文不读取、不上传、不存储。**
详见本文 2.16。

**Q：为什么需要开机自启？**
A：用户重启手机后同步要能自动恢复。而且只在他**之前主动开过同步**的情况下才自启，
他主动停止或退出登录后就不会再自启，完全受用户控制。详见本文 2.6。

**Q：为什么申请忽略电池优化？**
A：这不是静默提权，只是**跳转到系统设置页**让用户自己决定。
不加白名单的话，息屏（Doze）时同步会中断。详见本文 2.8。

**Q：剪贴板内容会不会上传到你们服务器？会不会拿去做别的？**
A：会在用户本人账号下的多设备之间中转同步，服务端加密存储（AES-256-GCM），
支持设备间端到端加密。**不做内容分析、不做用户画像、不用于广告、不向第三方共享。**
